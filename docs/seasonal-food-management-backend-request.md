# 제철 음식 관리 CRUD API 구현 요청

## 작업 범위와 현재 상태

관리자 화면 `/admin/seasonal-foods`를 제철 음식 관리 화면으로 재구성했다. 큐레이션/PICK 작성 페이지를 다시 만드는 작업이 아니라 음식 원본 관리다. 서버 구현은 이번 프론트 작업 범위에서 제외했다.

2026-09-18 원격 `plateAppServer`의 `origin/main`에 있는 `SeasonalFoodAdminController`를 확인했다.

| 기능 | 현재 서버 | 현재 관리자 화면 |
| --- | --- | --- |
| 목록 조회 | GET `/api/admin/seasonal-foods?page=0&size=50` | 모든 페이지를 읽어 검색·분류·상태 필터 제공 |
| 설명·사진 수정 | PUT `/api/admin/seasonal-foods/{id}` | 실제 저장 연결, version 전달 |
| 이미지 업로드 | POST `/api/admin/seasonal-curations/files` | 기존 공용 업로드 사용 |
| 신규 등록 | 없음 | 입력 화면만 준비, 제출 비활성화·미저장 안내 |
| 삭제 | 없음 | 확인창만 준비, 실행 비활성화 |
| 이름·분류·제철·공개 상태 수정 | 현재 PUT 대상 아님 | 기존 항목의 해당 필드는 변경하지 않음 |

미구현 API를 호출하거나 브라우저에만 저장한 뒤 서버에 저장된 것처럼 표시하지 않는다. 새 음식 입력은 메모리상의 미저장 입력이며 새로고침 시 유지되지 않는다.

## 요청 계약 — 아래는 신규 제안이며 기존 API가 아님

### 조회

- 목록 응답은 기존 `ApiResponse<AdminPageResponse<FoodView>>` 유지.
- GET `/api/admin/seasonal-foods/{id}` 상세 조회 추가. 목록 선택 시 최신 version을 받을 수 있게 한다.
- 목록·상세에 `months: number[]` 또는 합의된 제철 기간 필드를 추가한다. 현재 화면은 1~12월을 다중 선택하는 신규 등록 UI를 준비했다.
- 분류 코드 목록과 한글 이름을 메타데이터 API로 제공하거나 확정된 허용 코드 목록을 전달해 달라. 현재 신규 UI 분류는 초안이며 서버 enum 확정 후 일치시켜야 한다.
- 데이터가 많아지면 서버 검색 `keyword`, `categoryCode`, `status`, `month`와 페이지 정렬 계약도 추가한다. 현재 프론트는 잘린 첫 페이지만 검색하지 않도록 전체 목록을 조회한다.

### 등록: POST `/api/admin/seasonal-foods`

제안 요청:

```json
{
  "nameKo": "대하",
  "categoryCode": "CRUSTACEAN",
  "months": [9, 10, 11],
  "shortDescription": "음식 소개",
  "selectionGuide": "고르는 법",
  "storageGuide": "보관법",
  "cautionText": null,
  "afterSeasonText": null,
  "representativeImageUrl": "https://...",
  "representativeImageMobileUrl": null
}
```

- 초기 상태는 서버에서 `DRAFT`로 지정한다. 생성과 공개를 분리한다.
- 음식 이름 공백 제거·필수 검증·최대 길이, 분류 유효성, 제철 월 중복 제거 및 1~12 범위 검증 필요. 화면 이름 길이는 임시 100자이며 서버 규격 확정 필요.
- 설명 필드별 최대 5,000자, 이미지 URL 최대 1,000자는 기존 수정 계약과 동일하게 유지한다.
- 중복 이름 처리 기준을 확정하고, 중복을 막는 경우 명시적 409 코드와 필드 오류를 내려준다.
- 생성 결과는 `id`, `version`, `status`와 이미지 열람용 `imagePreviewUrl`, `mobileImagePreviewUrl`을 포함한 상세 응답으로 반환한다.
- 데이터베이스 제철 기간 테이블과 `months`의 매핑을 서버에서 책임진다. 비연속 월, 연말~연초, 윤년 마지막 날을 보존해야 한다. 월 단위가 부적절하면 일 단위 기간 계약을 먼저 회신해 달라.

### 수정: PUT `/api/admin/seasonal-foods/{id}` 확장

- 기존 설명·이미지 수정 클라이언트가 계속 동작해야 한다. 신규 필드를 생략했다고 기존 이름·기간·상태를 초기화하면 안 된다.
- `version` 기반 낙관적 잠금 유지, 충돌은 409. 입력 내용 재확인을 위한 최신 상세 조회 제공.
- 이름·분류·제철 기간 수정 가능 범위를 확정하고 추가한다.
- 공개 상태 변경은 별도 상태 API 또는 명시적 수정 필드로 계약을 정한다. 공개 시 필수 정보·이미지·기간 검증이 필요하다.
- 저장용 이미지 URL과 서명된 열람용 URL을 구분한다. 프론트는 열람용 URL을 저장값으로 보내지 않는다.

### 삭제: DELETE `/api/admin/seasonal-foods/{id}?version={version}`

- `SEASONAL_MANAGE` 권한, version 검증, 삭제 감사 기록이 필요하다.
- 연결된 PICK·큐레이션·콘텐츠가 있는 경우 우선 409와 연결 건수·대상 정보를 반환하는 방향을 제안한다. 연결 데이터를 묵시적으로 연쇄 삭제하지 않는다.
- 실제 삭제와 `ARCHIVED` 보관 처리는 구분해야 한다. 물리/논리 삭제 정책을 확정해 회신해 달라. 화면에 삭제 성공으로 표시한 뒤 서버에서 공개 데이터가 유지되는 모호한 처리는 피한다.
- 확정된 삭제 성공 응답을 받은 후에만 프론트 목록·선택 항목을 제거한다.

## 권한·오류·감사

- 목록·상세: `SEASONAL_READ`, 등록·수정·삭제·상태 변경: `SEASONAL_MANAGE`.
- 조회 권한만 있는 계정은 프론트 상세 열람은 가능하고 편집·등록·삭제 실행은 불가능하다. 서버에서도 독립적으로 강제해야 한다.
- 400 필드 검증, 401 인증 만료, 403 권한 부족, 404 삭제된 항목, 409 버전/참조 충돌을 구분한다.
- 생성자·수정자·시각·감사 로그를 기록한다. 파일 업로드 후 저장 실패 시 고아 파일 정리 정책도 기존 미디어 정책과 맞춘다.

## 연결 완료 인수 조건

1. 신규 입력 → 실제 등록 → 재조회·새로고침 후 유지 확인.
2. 편집 저장 시 해당 음식만 변경되고 원본 제철 관계가 보존됨.
3. 사진 파일 업로드 및 대표·모바일 미리보기, 저장 후 서명 URL 갱신 확인.
4. 삭제 취소 시 무변경, 삭제 성공 후 목록 제거, 연결 항목 삭제 충돌 처리.
5. 조회 전용·무권한 계정 및 version 충돌 테스트.
6. 서버 배포·계약 확정 후 프론트 등록/삭제 제출 활성화 및 기본 정보 수정 연결. 현재 비활성화된 UI만으로 서버 구현 완료를 판단하면 안 된다.
